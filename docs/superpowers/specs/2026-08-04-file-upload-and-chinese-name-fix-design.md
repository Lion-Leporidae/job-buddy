# 文件上传分类与中文姓名顺序修复设计

## 已验证问题

4399 简历页的“简历附件”使用隐藏的无 `id`、`name`、`accept`、`label` 文件输入。输入直属 `resume-file-module` 只显示已上传文件名，语义“简历附件”位于再上一层 `resume-module`。头像上传控件尚未渲染为同一个原生文件输入。旧分类器只使用标准信号，并把“允许图片格式”当作照片证据，招聘站允许图片简历时可能把求职照片写入简历附件。

个人资料使用 `firstName` 表示名、`lastName` 表示姓；现有 `derived.fullName` 固定为“名 姓”，不适合中文招聘页的“姓名”。

## 方案比较

### 文件上传

1. **最近独立上传区块优先（采用）**：从文件输入向上查找有限层级，将每层自身的短文本和类名作为候选；最近出现“简历/附件”或“头像/照片”的独立模块决定类型。`accept` 只验证照片框是否支持图片，不再独立决定类型。
2. 仅扩大 `nearbyText`：改动较小，但容易读取整个页面，同时出现“简历”和“头像”后再次误判。
3. 为 4399 写站点特例：当前页面准确，但无法覆盖其他秋招系统。

### 姓名顺序

1. **字段语义分流（采用）**：新增 `derived.fullName.zh`；“姓名、中文姓名、姓名全称”映射为“姓+名”，英文 `full name/name` 继续使用“名 姓”。独立“姓”和“名”字段保持原值。
2. 根据浏览器语言全局反转：简单，但中文浏览器访问海外网站时会错误。
3. 永久将 `derived.fullName` 改为姓在前：会破坏英文招聘页。

## 设计

- 新建纯函数 `classifyUploadField`，输入文件元素、标准信号和资料可用状态，输出简历、照片或未知。
- 语义优先级采用最近命中原则；同一短上下文同时命中时，明确“简历附件”优先于仅由文件名产生的“图片”字样。
- 图片扩展名、图片 MIME 和文件名中的“图片”都不能单独把未知上传框判为照片。
- 未识别的文件框不自动上传，避免对作品附件、成绩单或其他材料做错误写入。
- `resolveProfileValue` 负责生成无空格的中文全名：`lastName + firstName`。
- 字典将中文姓名词映射到 `derived.fullName.zh`，英文词继续映射到 `derived.fullName`。

## 验证

- 4399 风格 `resume-module > resume-file-module > input.hidden` 必须识别为简历，即使当前文件名是 JPG。
- 仅 `accept=image/*` 且没有照片语义时必须保持未知。
- “上传头像/证件照”识别为照片；“作品附件”保持未知。
- `张`（姓）与`三`（名）的中文姓名解析为“张三”，英文全名仍为“三 张”或资料原有英文顺序。
- 完整测试、类型检查与生产构建通过。
